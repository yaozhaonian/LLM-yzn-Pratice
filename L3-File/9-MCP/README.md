1. MCP 底层是完整双向 RPC 协议，不是简单 HTTP GET/POST
两种传输模式都有固定流程：
STDIO 本地模式（桌面客户端用）：父子进程通信，要管理进程生命周期、读写管道、JSON-RPC 消息封包；
SSE/HTTP 远程模式（内网 / 云端服务）：长连接会话、初始化握手、工具列表发现、流式返回。
原生 API 没有会话、自动工具发现、上下文隔离这些设计，所以更轻，但能力单一。
2. MCP 天生为「多模型、多客户端复用」设计，牺牲单次调用简洁性换取复用收益
对比两种开发模式取舍
| 方案 | 单次调用代码量 | 适用场景 | 麻烦与否 |
| :--- | :--- | :--- |
| 直接封装 Function Calling（原生 API） | 极少，几行 | 单一 AI 应用、只给一个大模型用、工具少 | 	简单 |
| 自建 MCP Server + 程序调用 | 多样板代码，异步会话 | 一套工具给 Cursor、私有 Agent、本地 Qwen、Claude 企业版共用 | 麻烦，但一次开发多处复用 |


举个现实例子：
如果你只做一个内部 LangChain Agent，只对接一套业务数据库：直接写 HTTP 工具最简单，没必要 MCP；
如果你公司同时用 Cursor 开发、内网 AI 客服、数据分析 Agent 三套 AI 系统，都要查同一张业务库：只写一套 MCP Server，三套系统全部直接接入，长期大幅减少重复代码。
