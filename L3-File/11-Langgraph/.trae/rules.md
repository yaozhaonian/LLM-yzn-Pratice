# ERP智能客服项目 代码生成全局规则

## 技术栈强制约束

1. 编程语言：Python 3.11+，严格遵循 PEP8 编码规范
2. 流程调度：LangGraph 作为多Agent状态机核心，定义节点与流转边
3. RAG能力：LlamaIndex 对接 Milvus 向量数据库，实现知识库检索
4. 大模型：统一通过 Ollama 调用本地 qwen2.5:7b 模型，封装为独立 llm\_client 模块
5. 业务数据库：MySQL 8.0，使用 SQLAlchemy ORM 操作，禁止字符串拼接SQL
6. 数据校验：所有接口入参、状态字段使用 Pydantic 做类型校验
7. 配置管理：所有地址、端口、密钥等配置统一从 .env 文件读取，禁止代码硬编码

## 代码编写规范

1. 所有函数、类必须包含完整中文 docstring，核心逻辑分支添加行内注释
2. 异常捕获必须明确指定异常类型，禁止裸 except，必须输出错误日志
3. 变量、函数使用蛇形命名法，类名使用大驼峰命名法
4. 单个函数代码不超过80行，逻辑复杂时必须拆分为多个子函数

## 架构分层强制要求

各层严格解耦，禁止跨层混用逻辑：

- graph/：仅存放 LangGraph 状态定义、节点注册、边流转逻辑，不写业务代码
- agents/：存放各业务Agent的提示词模板、调用封装
- services/：业务逻辑层，封装RAG检索、发货校验逻辑、数据聚合处理
- dao/：数据访问层，仅封装MySQL的原子增删改查操作
- config/：环境变量加载、全局常量定义
- utils/：通用工具函数（格式处理、日志、脱敏等）

## 输出约束

1. 生成代码时自动补全缺失的依赖导入语句
2. 输出完整可运行的代码，不写伪代码、占位代码
3. 涉及数据库表结构时，同步附带建表SQL说明

## 核心原则

- 架构优先、设计优先、真源优先、严格验收。
- 开始编码前必须先想清楚：为什么要这样做、这样做是否正确、是否存在更简单且更符合当前系统的做法。
- agent 必须敢于指出不合理的需求、错误的架构方向、冲突的规则和缺失的验收条件，帮助用户完善系统，而不是机械执行。
- 禁止补丁式开发：不得用散落 `if`、临时兼容分支、硬编码、`sleep`、全局 flag、prompt 文案、mock 或假数据绕过架构问题。
- 禁止无意义向后、向下兼容：旧字段、旧接口、旧产品残影若污染当前合同，必须先向用户说明取舍，不得擅自保留双路径。
- 禁止选项剧场：用户要求架构或方案时，给出一个推荐主线；备选方案只用于解释为什么不选。
- 禁止偷懒、糊弄和留尾巴。完成定义必须包含可验证结果、未闭合风险和下一步边界。
- 用户明确否定的概念必须从代码、文档、计划和命名中删除，禁止换个名字继续保留。
- 当用户说“先看”“不动代码”“先给判断”时，必须保持只读审查，直到用户明确要求执行。
